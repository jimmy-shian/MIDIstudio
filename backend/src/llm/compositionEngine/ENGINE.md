# Composition Engine

## 職責

Composition Engine 將使用者需求、Guideline Book 的音樂計畫和目前 `ProjectState` 轉成合法、可逐步執行的工具操作。它處理「怎麼做進工程」，不重新定義審美原則，也不維護第二套樂理資料。

## 輸入與輸出

- 輸入：使用者需求、目前工程摘要、工具 schema、樂理/工具知識。
- 內部計畫：意圖與限制、總長和段落、調性/速度、核心素材、聲部角色、操作順序。
- 輸出：符合 schema 的工具呼叫、依操作回報更新的下一步，最後是簡短中文摘要。

## 執行階段

### A. 讀取需求與現況

先辨認使用者要新作、續寫或局部修改。讀取目前調性、速度、小節數、track、音符和已存在素材；延續工程時保留使用者未要求改動的內容。必要參數缺失時，採用最少假設，不阻塞簡單任務。

### B. 建立可執行計畫

將創作計畫拆成與需求等長的段落/和聲安排，再決定哪些聲部需要新增或修改。操作要能回扣核心素材和段落功能。若需求是局部修改，計畫只涵蓋該範圍。

### C. 依賴順序寫入

1. 必要時設定調性與速度。
2. 需要和聲時建立和弦骨架，bars 等於使用者要求的總小節數；不得自行延長。
3. 寫入旋律、低音和節奏等聲部，讓聲部角色明確。
4. 最後才處理力度、音色或演奏細節。

不是每個任務都需要每一階段。不可為了遵循模板而覆寫無關設定。

### D. 驗證每批操作

工具呼叫必須經 `executeCompositionOps` 符合 schema 與 `validateOps` 規則後才寫入工程。trackId 和 note id 只能引用目前工程中的值。時間使用 beats；每次 `add_notes` 不超過 32 音；每個模型回合至多兩次工具呼叫。若驗證失敗，根據回報修正參數再試，不要重放已成功操作。

每批操作後，以工具回報和更新後工程為準。判斷尚缺哪一項必要工作，再呼叫工具；使用者需求已達成便停止。

### E. 交給 Critic

每批成功操作後，agent loop 要求模型用更新後工程而非原始計畫做品質檢查。總計最多 8 次模型呼叫：前 7 次可修改工程，最後一次禁用工具，專做 Critic 終檢和摘要。只對可由現有工程和工具操作修正的問題採取行動；如果工具能力不足以完成某項潤飾，保留已完成作品並在總結中清楚說明限制。

## 硬限制來源

MIDI 範圍、beats 定義、曲式/和弦數據以 `../musicKnowledge.ts` / `@midistudio/shared` 為準；操作合法性和批次上限以 `executeCompositionOps`、工具 schema 與 `validateOps` 為準；模型輪數由 `agentLoop.ts` 控制。文件不得暗示模型可突破這些限制。
